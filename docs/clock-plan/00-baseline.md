# C0：基线、所有权与安全试验样本

[返回总计划](../CLOCK-SYSTEM-IMPLEMENTATION-PLAN.md)。各卡默认遵守[总计划 3.5 共享约束](../CLOCK-SYSTEM-IMPLEMENTATION-PLAN.md#35-所有卡共享的默认约束)，卡内只写特有边界。状态：未开始。本阶段交付调查和基线，不新增硬件写入。

## 阶段目标与退出条件

使后续每个操作都能回答：基于哪份已验代码、谁在写、谁需要它、具体测试哪个资源、可写到什么程度。五张卡分别验收；建议顺序 C0-01→C0-02→C0-04→C0-05→C0-03；资料结论不能替代后续硬件验收。

### C0-01 锁定时钟计划的运行基线

- **目标**：建立可复查、可回退的时钟实施基线。
- **前置**：当前 b32 交接及原始产物可查；若采用较新基线，先解释其来源和已验范围。
- **需求与边界**：记录源码、构建树、内核／镜像、ADT、参数和日志来源；列出现有相关回归及已知失败。不修改控制器、编译选项或测试模式。
- **本地检验**：核对源码与构建树、产物 SHA 和日志新鲜度；运行适用现有回归，既有失败保留原始结果及原因，不借本卡修复。
- **实机检验**：已有对应基线实机证据完整时引用原记录；缺失或来源不匹配时才安排一次原模式启动，取得启动、USB／根卷、显示／触摸证据。
- **预期结果**：产出唯一基线条目和回退路径；不需要为纯计划文档重编 b32。
- **失败归属**：归 C0-01 的 source／artifact／log／baseline 项；来源未闭合时不能判断后续硬件功能。

### C0-02 建立现有时钟相关寄存器的所有权表

- **目标**：确定当前 GCC、DISPCC、apps RSC、display RSC 相关资源的实际写入者及交接边界。
- **前置**：C0-01。
- **需求与边界**：表中按资源列出寄存器集合、现有 writer、使用者、访问前置、已知继承状态、拟接收方。跟踪 SweetRPMh／SweetMDSS 及板级入口；只列当前存在的写路径，不把未来控制器功能混进来。
- **本地检验**：从每类已有写操作追到实际调用点；无归属项必须注明未知与查证方法。同一资源不得出现两个计划 writer；区分本地 GCC vote 与 RPMh 命令。
- **实机检验**：引用当前路径日志确认 apps／display 通道及消费者命中；若日志不能区分，仅登记待补观测项，不新增广域 MMIO 扫描。
- **预期结果**：得到迁移清单和旧方禁止写入的明确切换点；未知项可保留，但它们阻塞自己的交接。
- **失败归属**：归 C0-02 的 writer／access／consumer 项；冲突未清除时后续切换卡记 blockedBy=C0-02。

### C0-03 调查首批可安全操作的具体样本

- **目标**：给首批 GCC 门控及 apps RSC 请求选出可证实的实机样本，或明确证明当前尚无合格样本。
- **前置**：C0-02、C0-04（样本优先取清单内消费者实际需要的资源；清单外样本须说明理由）。
- **需求与边界**：样本卡记录 controller／ID、寄存器范围、当前 owner／使用者、父源／电源凭据、原状态、允许动作、完成观测、停止及撤回条件。首批只需一个本地普通 gate 和一个已有合法 apps 请求；voted、reset、PLL、GDSC 等在进入对应卡前补各自样本卡。
- **本地检验**：交叉核对 LG 参考、实际 ADT 与现有代码；“Linux 中 disabled”“软件引用为零”“没找到驱动”均不足以证明空闲。列出排除 UFS／USB／正在扫描显示等资源的理由。
- **实机检验**：仅对确认可访问的已知地址作最小只读核对，并使用既有自然请求证据；不为调查试着关闭、复位或重配资源。
- **预期结果**：每个首批样本得到“可实施／缺某项依赖／不适用”结论，附证据与解除门槛。没有安全样本时本调查可完成，对应写入卡仍受阻。
- **失败归属**：归 C0-03 的 identity／ownership／dependency／observation 项；不得把安全样本缺失写成门控算法失败。

### C0-04 建立消费者时钟需求清单

- **目标**：列出近期实际要实现或迁移的外设，以及每个外设所需的 clock／reset／domain／corner／带宽资源，作为后续阶段的实施顺序依据。
- **前置**：C0-02；项目当前外设计划（显示 PD4、触摸、USB、UFS 等）可查。
- **需求与边界**：按消费者列出资源 controller／ID、类型、所需操作（query／enable／disable／rate／reset／restore）、当前 writer、优先级及来源（LG 参考、ADT、现有代码）。区分“现有消费者迁移”和“新外设需求”。不为凑清单列入无近期计划的外设。
- **本地检验**：每项可追到具体参考或现有调用；与 C0-02 所有权表对得上；没有近期需求的阶段／卡明确标出。
- **实机检验**：无；纯调查。
- **预期结果**：得到按优先级排列的需求清单，并据此把无需求的卡标为“暂缓（无需求）”。C9-01 覆盖表以本清单为起点。
- **失败归属**：C0-04 consumer／resource-map／source。

### C0-05 判定各时钟控制器的适用范围

- **目标**：对 LG 参考树中的每个时钟控制器给出本设备的范围结论。
- **前置**：C0-01（ADT 来源已锁定）。
- **需求与边界**：逐一核对 GCC、RPMhCC、DISPCC、VIDEOCC、CAMCC、GPUCC、NPUCC（参考 dtsi `qcom,npucc` @0x9910000）、SCC（@0x2b10000，参考 dtsi 中 `status = "disabled"`）以及 debugcc（`qcom,debugcc-sm8150`）的实际 ADT 节点、窗口和消费者。参考树 disabled 本身不足以证明不适用，须结合实际 ADT／硬件证据。
- **本地检验**：每个控制器的结论为“首批／按需（C7 或 C9）／不适用／未知”，附来源；未知项写明查证方法。
- **实机检验**：无；只读引用已有 ADT 导出。
- **预期结果**：计划范围与实际芯片对齐，NPUCC／SCC 不再处于未提及状态。
- **失败归属**：C0-05 adt-node／source／scope。
